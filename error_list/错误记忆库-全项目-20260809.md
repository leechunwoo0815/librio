## 一、本轮新增错误（五要素）

### E-20260809-01 全量 pytest 顺序 flaky：全局 APScheduler 后台线程污染测试 stub/session
- 事实：TestClient 测试经 lifespan 启动全局 scheduler，每分钟任务经 monkeypatched
  `_get_db_session` 拿到同一 MagicMock/测试 session，额外调用 rollback/close——
  `assert_called_once` 失败 + 另一测试 DetachedInstanceError。单跑/组合跑全绿，全量 1 failed。
- 被抓方式：批末全量门禁（单跑绿 ≠ 全量绿）。
- 根因：测试假设"monkeypatch 的钩子只被被测代码调用"，未考虑全局后台线程共享该钩子。
- 修复：① scheduler 测试 fixture 一律 `stop_scheduler()`；② 共享钩子改 StaticPool +
  每次新 session 工厂（任务 close 不影响 fixture）。
- 防复发：凡 monkeypatch `_get_db_session`/`get_db` 的测试，先停全局 scheduler；
  全量跑是唯一验收（单文件绿不算）。

### E-20260809-02 F-105 测试互补数据缺陷（两口径结果相同，RED 不红）
- 事实：old_lost（exited 10 天前+update 本周）与新 lost（exited 本周+update 9 天前）
  构造互补：修复口径计 1、旧口径也计 1——断言 1 无法区分，撤修复不转红。
- 被抓方式：RED 实证不转红后逐值排查。
- 修复：拆两个独立用例（上周退出+本周刷字段 → 修复 0/旧 1；本周退出+上周刷字段 →
  修复 1/旧 0）。
- 防复发：测试数据必须让"新旧行为产生不同结果"，只造一组互补正例无效；
  RED 不转红 = 测试无效（承接 20260808 E-02 纪律）。

### E-20260809-03 F-018 扫描法教训复用：F-091 软删语义与 DB 唯一冲突
- 事实：应用层查重（只看活跃）放行软删复用，DB unique 拦截 → IntegrityError 500；
  与项目 user.phone 全局唯一语义（软删不复用）不一致。
- 处理：查重改为全局（含软删），语义对齐 user.phone。
- 防复发：加 DB 唯一约束前，先查同实体先例的软删复用语义并统一。

### E-20260809-04 修改 fixture 返回结构后未同步所有消费者
- 事实：db_factory 从 yield session 改为 yield (session, Session)，TestF110 使用处
  未同步解包（直接传元组给任务）→ 后续修正。
- 防复发：改 fixture 签名/返回结构后 `rg` 全部消费点。

## 二、终审整改复审增量（2026-08-09 当日晚）

> 来源：复审报告《专家意见/终审整改复审-20260809.md》+ 复审后修复批（5ed757c/51892d1/
> 58c3edf/eb8d913/3ff4ee3）。

### E-20260809-05 跨域误判：声称"已被 X 覆盖"未验证同域
- 事实：整改报告称 F-078 权益转让 reject"已被 F-080 行锁覆盖"——实际 F-080 的
  `_get_report_or_raise` 属 DamageAdminService（损坏定责域），与 benefit transfer 完全无关；
  reject 仍无锁，并发 approve+reject 可致"权益已转移但终态 REJECTED"。
- 被抓方式：复审逐项对照"声称覆盖点"的实际域归属（file:line 追到类名/表名）。
- 修复：reject 补 `.with_for_update()`（与 approve 对称）+ verify_mysql_concurrency 场景 J
  （撤行 FAIL 30/30 → PASS 0/29）。
- 防复发：复核"某修复已覆盖另一问题"时，必须验证**同服务/同表/同域**；跨域引用一律视为
  未经证实的声称。

### E-20260809-06 同类漏改复发：tencent dev 日志明文 phone（aliyun 同位置已修）
- 事实：F-020 只修了 aliyun/tencent 的 send_code 与通知成功分支，tencent send_notification
  的 dev 分支（SDK 未配置时触发）仍明文 `request.phone`——aliyun 同位置已修而 tencent 漏。
- 被抓方式：复审对"一类修复"全库 rg 所有同构调用点（防复发红线模式 1）。
- 修复：tencent dev 分支 `_mask_phone` + test_f020_sms_masking（tencent/aliyun 双守护）。
- 防复发：修脱敏/校验/过滤类问题时，**逐家供应商、逐分支**枚举（dev 分支常漏）；
  同类项测试必须覆盖所有调用点，不能只测第一个。

### E-20260809-07 Python logging：logger 级 filter 对传播 record 不生效
- 事实：F-021 把 TraceIdFilter 挂在 root logger，但任务内层 logger.info 经传播链到达 root
  handler 时**不执行 root logger 的 filter**（logging 只在发起 logger 上执行 filter）——
  任务内层日志 record 无 trace_id，HTTP 层靠 middleware 手动塞 request.state 掩盖了该缺陷。
- 被抓方式：新测试断言"任务内层日志 trace_id == 任务入口 trace_id"，getattr 为 None。
- 修复：filter 同时挂到 root 的 **handlers**（`hdlr.addFilter`）+ distributed_lock 设置
  `_trace_var` contextvar。
- 防复发：logging 的 filter 挂载点 = logger（发起方）与 handler（emit 前）两级；
  验证"传播链日志携带上下文"必须断言**最内层** logger 的 record 属性，不能只看外层消息文本。

### E-20260809-08 场景脚本基线污染：统计全表被前序场景干扰
- 事实：verify_mysql_concurrency 场景 K 用 `msg_type==3` 全表计数判定，前序场景（预约/借书）
  也产生同类消息 → 全量跑 FAIL 而单跑 PASS；场景 J 用固定 phone 前缀 `137{i:08d}` 与
  J 场景撞 user.phone 唯一 → 全量跑 IntegrityError。
- 被抓方式：单跑 PASS / 全量 FAIL 对照排查。
- 修复：判定改按场景独有内容过滤（`content LIKE '%逾期书%'`）；数据用随机 openid/phone。
- 防复发：场景脚本数据必须**唯一标识本场景**（内容标记/随机段），判定只统计本场景产物；
  固定枚举值（phone/isbn 序号）跨场景必撞唯一约束。

### E-20260809-09 文档数字漂移：基线与权威文档不同步（红线 6 复发）
- 事实：五件套/交接/PRD 中 pytest 910→925、ruff 494→496、迁移 043-055→056、
  MySQL A-I→A-K、evidence 41→42、borrow_limit "20 本"旧值（决策表/状态流转图/扫码枪规范）
  多处未随修复同步；部分历史审查文档无"现行基线指针"。
- 被抓方式：终审令维度 7（文档与声明审查）逐文件 grep 基线数字。
- 修复：全量对齐 + 历史文档补指针（`> 现行基线指针：...以项目交接-20260809 为准`）。
- 防复发：凡 pytest 数/ruff files/alembic head/迁移范围/证据文件数变化，全库 `rg`
  同口径数字核对（模式 6）；决策类旧值（如 borrow_limit 20→10）要在**全部 PRD 文档**同步，
  不只决策表确认依据。

### E-20260809-10 工具使用事故：edit 换行破坏（两次）
- 事实：用 edit 替换含尾部换行的片段时，两次把两行代码合并成一行（borrow 循环体、
  test_state_machines import）→ SyntaxError。均在提交前被全量门禁/ruff 抓出。
- 防复发：编辑含多行的代码块后，先 `python -c "ast.parse(...)"` 或跑该文件测试再继续；
  不把"编辑工具未报错"当"代码正确"。

### [F-20260807-058] review_submission 无锁读-改-写：并发审核同一提交可双计已读书数 + 覆盖审核结果 — P3 观察
- 级别: P3（观察项；管理端并发窗口，无资金风险，触发需两名审核员同时操作同一提交）
- 维度: R8 晋级链路 — 审核路径读-改-写锁覆盖（对照 F-053 cancel_order 同类模式）
- 文件: backend/domain/advancement/service.py:738-761（review_submission）；:470-484（increment_books_read 带锁）；backend/domain/advancement/models.py:80-91（ReadingSubmission status）
- 事实:
  ```python
  def review_submission(self, submission_id: int, data) -> dict:
      sub = self.db.query(ReadingSubmission).filter(ReadingSubmission.id == submission_id).first()  # L743-747 无 with_for_update
      sub.status = data.status        # L750 无条件覆盖

          self.increment_books_read(sub.child_id)   # L757 带锁 +1（ChildLevel 行锁）
  ```

- 证据: 两名审核员并发审核同一 ReadingSubmission：T1/T2 均读到 status=PENDING（无行锁）→ 均置 APPROVED → 各自 increment_books_read（此方法带 ChildLevel 行锁，两事务串行各自 +1）→ **books_read_at_level 双计** → 各自 check_and_advance（带锁，第二个事务重取 is_current 行已晋级则跳过）→ 提交。审核结果无状态守卫（无 affected==1 判定，无条件覆盖 L750），T2 覆盖 T1 的 comment/status 不报错。与 F-053（cancel_order 先查后改无锁）同为读-改-写模式，但为管理端低频路径（两名审核员同时操作同一提交概率低）。
- 影响: 一次提交被双计已读书数 → 加速晋级（若需 teacher_review 则 check_and_advance 提前 return None，影响限计数）；审核意见被后提交者静默覆盖。无资金/安全风险。SQLite 行锁 no-op，MySQL 下 T1 提交后 T2 的 increment_books_read 重取 ChildLevel 仍会 +1（计数在 ChildLevel 行上串行）——双计成立需 MySQL 实证。
- 建议: review_submission 对齐 F-053 修复模式：读 submission 带 with_for_update + 条件 UPDATE（WHERE id AND status=PENDING）按 affected==1 判定，拒绝重复审核；或至少对 status==APPROVED 分支加已审核守卫。
- 排重: F-053（cancel_order 先查后改无锁，订单域 P2）≠ 本项（审核域 P3，同模式不同面）；F-046（scheduler 直改状态）不涉；C-096（状态机矩阵）不涉审核并发。

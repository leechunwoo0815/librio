## [F-20260808-114] toggle_publish new_status 基于读值计算——并发双 toggle 状态停在同值（P3）

- **级别**: P3（弱观察；管理端低频 + 双端并发罕见；状态错乱可人工修正，无资金/安全）
- **位置**: backend/domain/book/service.py:352-373（toggle_publish）
- **类别**: 读-改-写非原子（模式⑦ 家族；R25 C-118 漏判复核修正）
- **事实**: toggle_publish 两步分离（L362 读旧值算 new_status → L365-366 SQL update 写计算值）——**SQL update
  原子只保证"写不撕裂"，不保证"翻转语义"**；并发双 toggle：
  - A 读 is_published=0 → new_status=1 → update 置 1
  - B 读 is_published=0 → new_status=1 → update 置 1
  - → 两次 toggle 状态停在 1（**本应回到 0**）——翻转失效
- **证据**:
  - service.py:362 `new_status = 0 if book.is_published == 1 else 1`（读旧值算翻转，在事务外）
  - service.py:365-366 `update(Book).where(id).values(is_published=new_status)`（写计算值）
  - 两步间无锁/无条件 update（对照 close_expired_orders F5 条件更新带 WHERE 前置——本条 WHERE 只 id 无
    is_published 前置，故双 toggle 双双通过）
  - **R25 C-118 漏判**：R25 判"SQL 原子更新——无读-改-写竞态 ✓"——只看了 update 原子性，**漏了 new_status
    计算时机**（读-算-写三步骤，翻转值来自事务外旧读）
- **触发**: 管理端并发双点击发布切换（双端同时操作/重试双击）
- **影响**: 发布状态停在错误值（本应翻转回 0 却停在 1）→ 已下架书保持上架（用户端可见）或反之；
  可人工再点修正。低频 + 罕见，P3
- **建议**: ① SQL 翻转更新 `is_published = 1 - is_published`（CASE 表达式在 DB 内原子翻转）；② 或条件更新
  `WHERE is_published == 旧值` 按 affected 判定（F5 模式）；③ 或 with_for_update 行锁串行化
- **排重**: R25 C-118 判"无竞态"为漏判（本条修正）；grep 无"toggle 翻转竞态"历史；F-053/F-058/F-080
  （先查后改无锁家族）同模式先例

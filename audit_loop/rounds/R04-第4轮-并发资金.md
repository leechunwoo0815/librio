### [F-20260807-053] cancel_order 先查后改无行锁：与支付回调并发可覆盖已 PAID 订单为 CLOSED — P2
- 级别: P2（代码证据充分；并发危害需 MySQL 实证，SQLite 行锁 no-op 不得据此下结论）
- 维度: R4 并发×资金 — Y.1 订单支付路径
- 文件: backend/domain/order/service.py:754-764
- 事实:
  ```python
  order = self.order_repo.get_by_id_or_raise(order_id)   # L756 无 with_for_update
  if order.pay_status != 0: raise ValidationError(...)   # 读内存快照 PENDING
  order.pay_status = PayStatus.CLOSED                     # L761 无条件 ORM 赋值
  self.db.commit()
  ```
- 证据: get_by_id_or_raise（base_repo.py:64）内部 get_by_id 无锁；Order 模型无 version_id 列（grep 全库 0 处 version_id_col，ORM 提交生成无条件 UPDATE）；对照 scheduler close_expired_orders（scheduler.py:918-928）用 `Order.pay_status == PENDING` 条件更新防"先付后关"（F5 修复）；cancel_order 为模式 1 同类漏改。
- 触发: 用户点取消订单的同时，微信支付回调到达——T1(cancel) 读 PENDING 快照 → T2(callback, with_for_update L425) 置 PAID 提交 → T1 以内存快照写 CLOSED 覆盖已提交的 PAID。
- 影响: 用户已扣款但订单被标 CLOSED；会员激活事件（OrderPaidEvent）已随 T2 发布，会员可能已开通——账实不一致，需人工对账纠偏。资金无直接丢失（钱在系统），但状态机被并发破坏。
- 建议: cancel_order 改条件更新（`filter(id=..., pay_status=PENDING).update({pay_status: CLOSED})`）或查询补 with_for_update + 提交前复查状态；与 scheduler 关单范式对齐。
- 排重: R1 F-005/006（押金退款时序）非本路径；F-008 仅报 FAILED 出路（状态机角度），未报并发覆盖；F-046（定时任务直改状态）非用户侧路径；全库 version_id 0 处确认无乐观锁兜底。

### [F-20260807-054] repay_deposit 仅拦 PAID：PENDING/REFUNDING 状态可重复创建押金单，child.deposit_status 无锁覆盖 — P3 观察
- 级别: P3（观察项；触发需重复点击 + 精确时序，无直接资金丢失路径）
- 维度: R4 并发×资金 — Y.2 押金路径
- 文件: backend/domain/deposit/service.py:257-259（拦截条件）→ :272-281（创建 + child 写）
- 事实:
  ```python
  existing = self.deposit_repo.get_active_by_child_for_update(child_id)  # L257 锁
  if existing and existing.status == DepositStatus.PAID:   # L258 仅拦 PAID
      raise ConflictError("押金已缴纳，无需重复缴纳")
  ...
  child.deposit_status = DepositStatus.PENDING             # L280 child 写（L249 读时无锁）
  ```
- 证据: pay_deposit（L79-83）对 PENDING stale 有 F78 复位逻辑后放行、非 stale 拦截"押金已缴纳"；repay_deposit 缺少同款——existing 为 PENDING（支付中/放弃未超时）或 REFUNDING/REFUND_PENDING 时均放行创建新 PENDING 单。child 行 L249 查询无 with_for_update（L280 写依赖 L249 读快照）。reset_stale_pending_deposits（scheduler 1:30）只复位超时单，双 PENDING 窗口内回调/即时支付可能双激活。
- 触发: 用户押金 DEDUCTED/REFUNDED 后重复触发重新缴纳（连点/双端），或 PENDING 支付中再次发起——创建第二张 PENDING 押金单。
- 影响: 多张 PENDING 押金单并存（get_active_by_child 视 PENDING 为活跃，后续操作取第一条，另一条滞留）；极端时序下 child.deposit_status 被覆盖回 PENDING 与真实记录状态不一致。无直接资金丢失（微信侧幂等 + 对账兜底）。
- 建议: repay_deposit 拦截条件对齐 pay_deposit——existing.status in (PAID, PENDING) 均拦截（或 PENDING stale 先复位）；child 查询补 with_for_update。
- 排重: F78（pay_deposit stale 复位）只覆盖 pay 路径，repay 为同类漏改；F-030（pay_deposit 网关失败覆盖回调窗口）非本路径；R1 2.1 押金状态机（C-005/F-005/006）未覆盖 repay 重复创建面。

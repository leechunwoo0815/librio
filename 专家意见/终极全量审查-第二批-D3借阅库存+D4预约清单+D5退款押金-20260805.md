## 二、P0 问题（上线阻断级，全部本人亲验）

### F35【资金/账】每日逾期任务整体覆写 `outstanding_fines`，抹掉丢失/损坏/手工罚款

- **证据（本人亲验）**：`backend/tasks/scheduler.py:1544-1567`——按孩子汇总时只统计 `status==OVERDUE` 记录的 fine_amount，然后 `child.outstanding_fines = fine_map.get(child.id, ...)` **直接赋值**；对照全库其他写入点（`deposit/service.py:430/479`、`damage_admin_service.py:84/160`）均为增量 `+=` 语义。
- **后果**：丢失赔偿 150 元经定责计入 outstanding 后，次日孩子任意一本书逾期被任务处理 → outstanding 被覆写为"当前 OVERDUE 罚款之和"（宽限期内甚至为 0），150 元静默蒸发。资金内控断裂。
- **修复方向**：任务只维护"逾期服务费"部分（增量差额调整），或 outstanding 的权威口径改为"全部未缴来源重算"而非仅 OVERDUE 借阅。

### F36【资金/账】还书时的逾期服务费从不计入 `outstanding_fines`（PRD §7.3 B11 未闭环）

- **证据（本人亲验）**：`backend/domain/borrow/service.py:215-258` `return_book` 只 `apply_fine` 写 record，无任何 outstanding_fines 写入（全库 grep 佐证，borrow 域零写入点）；F35 的覆写逻辑又只统计 OVERDUE 状态记录——已归还书的罚款两头都不进账。
- **后果**：逾期书在凌晨任务跑批前归还，服务费只留在 `record.fine_amount` 上，退押金/退款抵扣（E7/B11）全部抵扣不到——罚款体系对"按时还书的逾期者"完全失效。
- **修复方向**：`return_book` 中 fine_amount>0 时 `child.outstanding_fines += fine`（行锁），与 F35 同批整改（同写字段，必须统一口径设计）。

### F37【资金】订单退款 `total_amount` 传退款额而非原单额 + 网关拒绝被静默吞掉——生产部分退款 100% 失败且无人发现

- **证据（本人亲验）**：`backend/domain/refund/service.py:238-247`——`total_amount` 与 `refund_amount` 都传 `yuan_to_cents(amount)`（amount=退款额，函数签名 :206-207）；微信 V3 要求 `amount.total`=原订单实付，否则报错 268892183「订单或退款金额不一致」。对照 600 奖励退款的正确写法（`deposit/service.py:756-758` 用 `record.amount + refund_amt` 还原原单 1200）。且 `pay_v3.refund` 对被拒**返回 success=False 不抛异常**（`pay_v3.py:301-306`），而 `_execute_wechat_refund` **不检查 result.success**（对比押金侧有检查 `deposit/service.py:601-604`）→ 拒绝被当成"已提交"，退款单永挂 APPROVED。
- **后果**：凡按天扣费的退款（观察期第 8 天起 466.67 类、会员 5059.73 类、E7 抵扣后）在生产**笔笔被微信拒绝且静默**，7 天后才由 alert_stale_refunds 告警（还发错对象，见 F72）。
- **掩盖链**：DEBUG 分支直接 return（:223-226）+ Mock 恒成功 + **Gate 12 反向钉死错误语义**（`test_payment_gateway_contract.py:159-161` 断言 total==refund==50000，恰好全退时两值相等，测不出部分退款）。
- **修复方向**：`total_amount` 改用订单原额（order.amount 传入）；检查 `result.success`，False 走现有失败回退分支；Gate 12 补部分退款用例（total=原额、refund=部分）。

### F38【资金】`out_refund_no` 不落库、每次重试新生成——重复退款（钱多出）

- **证据（本人亲验）**：`refund/service.py:236` 每次执行 `RF{uuid}` 新生成；押金两处退款调用根本不传 out_refund_no（`deposit/service.py:592-599`、`:752-761`），由 `pay_v3.py:281` fallback 生成一次性 uuid。微信按 out_refund_no 幂等，官方明确要求"失败重试使用原商户退款单号"。而失败回退路径（`refund/service.py:264-265` 等）恰恰允许重审重试。
- **后果**：首次请求已到达微信但响应超时 → 重试产生**第二笔真实退款**（钱多出）；且退款单号不留存无法对账；已提交微信但回退 PENDING 后微信推 SUCCESS 回调时 `mark_refunded` 只认 APPROVED/COMPLETED → 409 → 微信重试风暴，钱已退系统显示未退。
- **修复方向**：out_refund_no 持久化到 RefundApplication/DepositRecord（申请时生成、重试复用）；补 query_refund 对账任务。

### F39【资金/机制】`pay_deposit` 无条件发布 DepositPaidEvent——生产环境未付款即获得借书资格

- **证据（本人亲验）**：`backend/domain/deposit/service.py:152-164`——`event_bus.publish(DepositPaidEvent)` 在 `if is_instant:` 块**之外**；事件同步执行，handler 无条件 `child.deposit_status = PAID`（`events/order_handlers.py:154-169`）；生产网关 `supports_instant_payment=False`（`pay_v3.py:67-69` 本人核读），即创建 prepay 单成功后、用户一分钱未付，孩子押金状态已 PAID，借书校验直接通过（`borrow/service.py:73-78`）。若用户放弃支付，无任何任务复位该状态（scheduler 只巡检 REFUND_PENDING，:1322-1332）→ 永久无押金借书。对照 `repay_deposit` 正确地把发布放在块内。
- **掩盖**：全部 deposit 单测 mock `supports_instant_payment=True`（`tests/unit/test_deposit_service.py:44`），非即时路径从未被执行。
- **修复方向**：发布移入 `if is_instant:` 块内；补 PENDING 超时清理任务（或押金状态对账）。

## 三、P1 问题（流程断裂 / PRD 明确条款未实现，全部本人亲验）

### F40 取消预约不拦 EXPIRED/FULFILLED → 库存双重释放/幻影库存

- 证据：`backend/domain/reservation/service.py:453` 只拦 `status == 3`（且是魔法数字）；EXPIRED(2)/FULFILLED(1) 放行置 CANCELLED 并发 ReservationCancelledEvent → `events/borrow_handlers.py:71-76` 无条件 +1。已过期预约过期时已 +1（:63-68），再取消又 +1；已取书的取消后书在孩子手里库存 +1，还触发等候名单通知（幻影库存）。
- 修复：cancel 只允许 PENDING→CANCELLED（条件 UPDATE `WHERE status=PENDING`），魔法数换枚举。

### F41 每日库存对账抹掉预约占用（PRD 口径矛盾，须先定口径再改码）

- 证据：`scheduler.py:289-318` reconcile_stock 把 available_stock 重置为 `count(copies AVAILABLE)`；而预约锁只体现在计数 -1（副本全程 AVAILABLE）→ 每晚 3:00 所有 PENDING 预约的锁被静默回补，次日可超卖。**PRD 附录 D.4 伪代码与 D.2 #4 自相矛盾，代码忠实实现了 D.4**。
- 专家裁定建议：available 口径 = 在馆副本数 − PENDING 预约数（对账同步扣除），请甲方/产品确认后改码。注意与 F44 的互相掩盖效应（见下）。

### F42 手动取书产生 `book_copy_id=None` 孤儿借阅：副本不动 + 无法扫码归还

- 证据：`reservation/service.py:160-164`（无 barcode 放行，book_copy_id=None）；`admin_borrow_router.py:419`（管理端"完成预约"固定无条码）；`borrow/service.py:200-211`（scan_and_return 按 book_copy_id 匹配，孤儿记录永远扫不到）；该行为被测试固化（`test_fulfill_barcode.py:138-147`）。
- 后果：书物理借出但无副本转 BORROWED，架上副本可被再次借出（物理同一本借两次）；归还只能手工按记录 ID。
- 修复：手动取书强制绑定一本 AVAILABLE 副本。

### F43 管理端扫码取书（PRD §8.2 主路径）必然 422，完全断路

- 证据：`backend/static/admin/js/pages/reservation.js:134` 只 POST `{barcode}`；`admin_schemas.py:594-600` FulfillReservationRequest 要求 reservation_id+child_id 且 `extra="forbid"` → 422；路由 `admin_borrow_router.py:411-420` 也只透传 reservation_id，barcode 丢弃；child_id 必填却从不使用。
- 修复：schema 增 barcode 可选字段并透传 ReservationFulfillRequest。

### F44 还书事件不带 `book_copy_id`——副本永不回 AVAILABLE，且借过一次的副本永远无法再借

- 证据（本人亲验）：`borrow/service.py:247-254` return_book 发 BookReturnedEvent **不传 book_copy_id**（事件类有该字段 `common/events.py:112`）；scan_and_return 也委托 return_book（:213）；唯一把副本置回 AVAILABLE 的 handler 依赖 `event.book_copy_id`（`borrow_handlers.py:31-40`），而库存 +1 走 `event.book_id` 照常发生（:42-46）。
- 后果：凡绑定副本的借阅，归还后副本永远 BORROWED——该物理副本扫码再借被五态校验拦截（`borrow/service.py:112-141`），可借副本随借阅次数单调递减；库存计数与副本状态持续背离，每晚被 F41 的对账"抹平"，两个 bug 互相掩盖。扫码 SOP 下这是上线即炸的链路。
- 修复：return_book 发事件带 `record.book_copy_id`。

### F45 预约取消/过期/取书三方竞态：check-then-act 无锁无条件更新

- 证据：fulfill 的预约读取无行锁（`reservation/service.py:136-149`，base_repo 普通 get）；expire_reservation 同样无锁（:202-218）；cancel 有锁但只拦 status==3（F40）。对照组 close_expired_orders 已用条件 UPDATE（F5 修复模式）。

- 修复：三处统一条件 UPDATE `WHERE id=? AND status=PENDING`，按 affected rows 判定。

### F46 预约创建缺"已有同书未还借阅"拦截（PRD 明确要求）

- 修复：create 时加同书活跃借阅校验。

### F47 首次扫码建档借书必 500：`Book.author` NOT NULL 但未传（已运行时复现）

### F48 丢失定级"待复核"期间登记找回/换新，冲销孩子其他合法罚款

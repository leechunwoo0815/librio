## 🔴 P0 — 必须修复

### P0-1: CheckIn 表缺少唯一约束 → 并发重复打卡

**文件**：`backend/domain/reading/models.py` CheckIn 模型  
**现象**：`check_in` 表只有普通索引，无 `UniqueConstraint(child_id, check_date, check_type)`  
**代码层 TOCTOU**：`_check_auto_checkin`（service.py:306）先 `get_today_checkin_by_type` 查询，再 `create` 插入。两个并发请求同时通过 `existing is None` 检查后都执行插入 → 同一孩子同一天同一类型插入 2 条打卡  
**影响**：打卡数据重复 → streak 计算虚高 → 统计偏差 → 可能影响奖励发放  
**对比**：`ReadingProgress` 有 `UniqueConstraint("child_id", "book_id")`，`UserVocabulary` 有 `UniqueConstraint("child_id", "word_id")`，唯独 `CheckIn` 缺失  
**修复建议**：
1. 加 Alembic 迁移：`UniqueConstraint("child_id", "check_date", "check_type", name="uq_child_date_type")`
2. 在 `_check_auto_checkin` / `_check_voice_checkin` / `_check_finish_book_checkin` 的插入处加 `IntegrityError` 捕获，冲突时静默跳过

### P0-2: reading/service.py finish_book 的 total_books_finished += 1 无行锁

**文件**：`backend/domain/reading/service.py:189-191`  
**现象**：读完书时 `child.total_books_finished = (child.total_books_finished or 0) + 1`，child 查询无 `with_for_update()`  
**对比**：`child/service.py:383` 的 `update_reading_stats` **有** `with_for_update()`；`deposit/service.py:420`、`refund/service.py:316`、`admin/services/damage_admin_service.py` 多处都有锁  
**影响**：并发读完多本书时 lost update → total_books_finished 偏差  
**修复建议**：改为调用 `child_service.update_reading_stats(books=1)` 或在查询处加 `.with_for_update()`

### P0-3: admin/borrow_service.py clear_child_fines 的 outstanding_fines = 0 无行锁

**文件**：`backend/domain/admin/services/borrow_service.py:25-33`  
**现象**：`child.outstanding_fines = 0` 查询无 `with_for_update()`  
**影响**：与管理端罚款操作（如 damage_admin_service 的罚款计入）并发时 lost update → 罚款金额丢失  
**修复建议**：child 查询加 `.with_for_update()`

## 🟡 P1 — 应修复

### P1-1: JWT 时区 aware UTC 与业务 naive 本地时间混用

**文件**：`backend/middleware/auth.py` / `admin_auth.py`  
**现象**：JWT 的 `exp`/`iat` 用 `datetime.now(timezone.utc)`（aware UTC），业务代码全部用 `datetime.now()`（naive 本地时间 GMT+8）  
**风险**：
- JWT exp 按 UTC 计算，如果 Python 比较时 naive 与 aware 混用，行为依赖具体上下文
- `python-jose` 的 `decode` 内部会做 UTC→naive 转换，但若服务器时区不是 Asia/Shanghai，exp 判定会有偏差
- 目前测试全在本地 SQLite + GMT+8 环境，跨时区部署会出现问题

**修复建议**：统一为 `datetime.utcnow()`（naive UTC）或全改为 aware（需同步修改 `base_model.py` 默认值 + 所有业务代码 79 处 `datetime.now()`）

### P1-2: total_revenue: float 违反"金额禁 float"红线

**文件**：`backend/domain/admin/admin_schemas.py:69`  
**现象**：`AdminDashboardResponse.total_revenue: float = 0`  
**实况**：`dashboard_service.py:210` 实际值是 `Decimal`，Pydantic V2 隐式转 `float` → 精度丢失  
**影响**：Dashboard 展示金额精度降低，极端情况下可能出现一分钱偏差  
**修复建议**：改为 `total_revenue: Decimal = Decimal("0")` 或 `total_revenue: str = "0"`

### P1-3: Redis 降级策略过于激进

**文件**：`backend/common/distributed_lock.py:36`  
**现象**：Redis `ConnectionError` 时降级为无锁执行（`yield True`）  
**风险**：
- 多实例部署时 Redis 挂掉，所有定时任务同时在各实例执行 → 重复执行/数据竞争
- 只捕获 `redis.ConnectionError`，未捕获 `redis.TimeoutError`、`ConnectionPool` 耗尽等异常
- 降级策略等于关闭分布式锁，与 `@distributed_lock` 的语义矛盾

**修复建议**：
1. 增加 `redis.TimeoutError` 和 `redis.RedisError` 捕获
2. 考虑降级时 `yield False`（跳过执行）而非 `yield True`（无锁执行），或通过配置项控制降级行为

### P1-4: LIKE 通配符注入（多处）

**文件**：`backend/domain/admin/services/` 多处  
**涉及**：
- `order_service.py:61` — `like(f"%{search}%")`
- `borrow_service.py:318-321`
- `book_service.py:207`
- `user_service.py:44-51`
- `system_service.py:132`

**现象**：SQLAlchemy 参数化防 SQL 注入，但 `%`/`_` 通配符未转义。用户搜索 `100%` 会匹配所有包含 `100` 后跟任意字符的记录  
**影响**：搜索结果不准确，可能被恶意利用做信息探测  
**修复建议**：搜索关键词中转义 `%` 和 `_`：`search.replace('%', '\\%').replace('_', '\\_')`，并在 `like()` 中指定 `escape='\\'`

## 🟢 P2 — 建议修复 / 低风险

### P2-1: security/router.py check_text 未检查 detail 字段

**文件**：`backend/domain/security/router.py`  
**现象**：微信 `msg_sec_check` v2 返回的 `detail` 中 `suggest: "risky"` 未检查，只检查 `errcode == 0`  
**影响**：违规内容可能漏判（低危，微信 API 已做主判定）  
**修复建议**：补充检查 `detail[].suggest == "risky"` 时也拒绝

### P2-2: Quiz score Decimal 与 float 比较精度风险

**文件**：`backend/tasks/scheduler.py:355-356`  
**现象**：`pass_score = float(pass_rate) * 100`，然后 `Quiz.score >= pass_score` 比较。`Quiz.score` 是 `Numeric(5,2)`（Decimal），与 `float` 比较依赖 Python 隐式转换  
**影响**：边界值（如 `80.0`）理论上可能因浮点精度出现判断偏差  
**修复建议**：`pass_score = (pass_rate * 100).quantize(Decimal("0.01"))`，保持 Decimal 比较

### P2-3: WeChat access_token 进程内缓存多实例问题

**文件**：`backend/domain/wechat/service.py`  
**现象**：`_AccessTokenCache` 是进程内内存缓存，多 worker/多实例部署时每个进程独立缓存 → access_token 被多次刷新（每次刷新使旧 token 失效）  
**影响**：微信 API 调用次数增多，极端情况可能触发频率限制  
**修复建议**：改用 Redis 存储 access_token（带 TTL），多实例共享

### P2-4: 退款异步执行的时间窗口

**文件**：`backend/domain/refund/service.py:206-278`  
**现象**：`audit_refund` 先 commit（refund.status = APPROVED），然后 BackgroundTasks 异步执行 `_execute_wechat_refund`。退款失败时才回退为 PENDING  
**风险**：commit 到异步任务执行之间有一个短暂窗口，查询会看到 APPROVED 但实际即将失败  
**影响**：低（异步任务通常秒级执行），但严格来说不是原子操作  
**修复建议**：可接受现状；如需严格一致，改为同步执行或引入 "PROCESSING" 中间状态

### P2-5: 迁移文件编号重复

**文件**：`alembic/versions/`  
**现象**：两个 `030_` 前缀（`a1b2c3d4e5f6` 和 `a3f5c8d91e02`），两个 `027` 前缀  
**影响**：不影响 alembic 运行（按 revision hash 排序），但影响可读性和维护  
**修复建议**：重命名文件前缀使其唯一

### P2-6: teacher 域代码结构不对称

**现象**：`backend/domain/teacher/` 目录不存在，teacher 相关代码在 `backend/domain/admin/services/teacher_service.py`。但 alembic 有 `007_teacher_model` 迁移，表存在  
**影响**：文档宣称的 27 个域与实际目录结构不符，新开发者可能困惑  
**修复建议**：统一文档描述，或将 teacher service 移到独立域目录

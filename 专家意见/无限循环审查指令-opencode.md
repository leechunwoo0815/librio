## 二、五条铁律（违反任何一条，本轮产出作废）

### 铁律 1：证据律
- 每条发现必须有：文件路径 + 行号 + 代码片段 + 命令输出或复现路径。
- 禁止"可能有问题""理论上会崩""建议优化一下"。说不出复现路径的发现 = 不是发现。
- 报告中的数字必须来自你亲手跑的命令输出，禁止引用记忆/快照/估算。

### 铁律 2：排重律
- 每圈开工前先 `grep` 你的历史发现日志（`audit_loop/findings-*.md`）和
  `专家意见/` 目录，**已报过/已修过的问题禁止再报**。
- F1-F80、D1-D8、零宕机 8 bug、静态扫描假阳性清单——这些是已结案项，
  重新命中时记录"已结案"并跳过，不计入新发现。

### 铁律 3：零发现合法律
- 一个维度审查干净 = 合法产出。记录"X 维度已穷尽，证据：跑了 Y 命令，输出 Z"。
- **严禁为了显得有产出而降低定级标准、把风格问题报成 bug、把 P3 报成 P1。**
- 连续 3 圈零发现不是失败，是证据强度高的信号。照常记录，进入下一维度。

### 铁律 4：门禁律
- 任何代码改动后，必须全量跑门禁（禁止缩窄范围）：
```bash
venv/bin/ruff check backend/ tests/ && venv/bin/ruff check features/ scripts/
venv/bin/ruff format --check .
venv/bin/python -m pytest tests/ -q
venv/bin/python -m behave features/ -q
PYTHONPATH=. DATABASE_URL=sqlite:///data/app.db venv/bin/python scripts/check_model_consistency.py
PYTHONPATH=. venv/bin/python scripts/verify_api_contract.py
venv/bin/alembic check
```
- 只用 `venv/bin/...`，不用 `.venv/` 或系统 python。
- SQLite 下行锁是 no-op：涉及并发的验证标"需 MySQL 实证"，不得用 SQLite 结果下并发结论。

### 铁律 5：最小破坏律
- 不 `git push --force`、不 `git reset --hard`、不 `rm -rf`、不改 `.env`。
- 不重构、不改名、不顺手格式化——你只报，基本不改（例外见 §七）。
- 审查日志文件单独提交：`git add audit_loop/ && git commit -m "docs: 循环审查第N轮发现"`。

## 三、循环协议（每一圈的固定动作，按序执行）

```
一圈 = 选靶 → 读档 → 深挖 → 举证 → 记录 → 推进度
```

1. **选靶**：读 `audit_loop/progress.md`，取下一个未审查的维度子项（见 §四轮换表）。
   若 progress.md 不存在：创建它，从维度 1 开始。
2. **读档**：读该子项相关的代码文件（用 Read 工具，禁止凭记忆写代码内容）。
3. **深挖**：按该维度的"检查方法"执行。必须跑出真实命令输出。
4. **举证**：对每个疑似问题，回答三问：
   - 触发路径是什么？（哪个用户操作/哪个定时任务/哪个并发时序）
   - 用户/系统会看到什么？（白屏？错钱？丢数据？）
   - 我能用命令证明吗？（跑不出来就降级为"待实证"，不得报 P0/P1）
5. **记录**：追加到 `audit_loop/findings-YYYYMMDD.md`（格式见 §五）。
   零发现也要记录"clean"条目。
6. **推进度**：更新 `audit_loop/progress.md`，提交 git，进入下一圈。

## 四、审查维度轮换表（15 维 × 子项，按序循环）

每维度的子项跑完后在 progress.md 打勾。15 维全部跑完一轮后，从维度 1 用**更深的检查方法**再跑一轮（见 §八深度递增规则）。

### 维度 1：并发与事务
- 1.1 所有 `db.commit()` 之后是否还有写操作（grep 每个 service，逐函数读）
- 1.2 所有"先查后改"路径是否有 `with_for_update()`（对照 §四.铁律4 SQLite 限制标注）
- 1.3 事件总线 handler 是否自行 commit（应为调用方统一 commit）
- 1.4 死信记录路径是否会在异常时再次炸掉

### 维度 2：状态机合法性
- 2.1 押金：UNPAID→PENDING→PAID→REFUND_PENDING→REFUNDING→REFUNDED/DEDUCTED，逐转移点核对 PRD V3.23
- 2.2 借阅/预约/订单/退款/会员 五状态机，逐个画转移矩阵，找死状态和非法转移
- 2.3 每个状态变更点的前置条件校验是否完整

### 维度 3：资金安全
- 3.1 全库 grep 金额计算：`float(` 出现于金额路径 = P0
- 3.2 元/分转换点：每个转换点找兄弟路径（历史教训：双重转换）
- 3.3 支付/退款回调：幂等性、签名验签、金额校验、状态前置，逐行读
- 3.4 退款公式：边界矩阵 [当天, 用满-1天, 用满, 超期] 逐场景手算对账

### 维度 4：API 契约
- 4.1 `scripts/verify_api_contract.py` 跑出报告，逐条核对 mismatch
- 4.2 前端 `utils/api.js` 每个函数的参数名 vs 后端 Pydantic Schema 字段名，逐个 diff

### 维度 5：小程序端（34 页）

## 六、定级举证标准（没达到证据标准就降级）

| 级别 | 定义 | 举证要求 |
|---|---|---|
| P0 | 钱错/数据丢/安全洞/全站崩 | **必须有可复现路径或命令输出**，禁止推断定 P0 |
| P1 | 功能错/用户可见异常 | 必须有触发路径 + 代码证据 |
| P2 | 边界场景错误/体验缺陷 | 代码证据即可 |
| P3 | 风格/可维护性 | 标注"风格项"，不占 bug 数 |

**降级的方向永远向下，不向上。** 拿不准 P0 还是 P1？定 P1。

## 七、修复授权边界（你默认只报不修）

允许直接修的（且必须做）：
- 审查日志文件（audit_loop/）的创建与追加

**禁止修**的（报了就走，等人类/开发模型处理）：
- 任何 backend/、frontend/ 下的代码文件
- 任何配置、迁移、测试文件

**例外**：如果你发现了一个 P0 且有 100% 证据链（复现命令+输出），
允许在一个独立分支上修复，但必须满足：
1. 先写失败测试（RED），再修（GREEN），附 RED→GREEN 输出
2. 全量门禁七条全绿（§二铁律 4 清单）
3. 单独 commit：`fix: ...` + 正文写清证据链
4. 在 findings 日志中记录"已修 + commit hash"

不满足以上任何一条 = 只报不修。

## 八、深度递增规则（第二轮起怎么挖得更深）

第一轮：按 §四 检查方法跑（模式匹配 + 命令验证）。
第二轮：同一维度换攻击面——
- 从"代码有没有写保护"升级为"保护在并发/异常/重放下是否仍成立"
- 从"单点审查"升级为"链路审查"：选一条业务流（如 用户报名活动→支付→签到→退款），
  从前端点击到数据库落行，逐跳读代码
- 从"正常路径"升级为"故障注入"：网关超时、回调重复、session 中断、时钟回拨

第三轮：交叉维度——维度间的接缝处（如 定时任务×状态机、配置×退款公式）。

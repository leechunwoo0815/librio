# 强制闭环自审协议（LOOP-2）设计 · 2026-08-09

> 需求：让能力有限的执行模型在无人值守下完成"全量审查→修复→验证→测试"闭环，
> 验证不通过不得进入下一项，全部闭环前不得停工，最终输出交付报告。
> 本文档是机制设计说明；执行入口是 `audit_loop/loop2/PROMPT.md`，外层驱动是
> `audit_loop/loop2/driver.sh`。

---

## 一、为什么弱模型靠"自觉"做不成闭环

R1-R160 的前代 loop（DeepSeek v4 flash + opencode）能跑完 160 轮，是因为它**只报不修**：
任务单一、无状态转移、无"通过"裁决权。一旦要求"审查+修复+验证"全包，弱模型的三个失效点：

1. **裁决权在模型脑子里**——它会读一遍测试输出然后宣布"通过"，甚至弱化断言凑绿
   （本项目 E-02"RED 不转红=无效测试"、模式 4 假测试全是这类）。
2. **状态在模型脑子里**——上下文截断/换会话后忘记干到哪，重复劳动或漏项。
3. **没有停机条件**——要么提前宣布完工，要么在一项上无限打转烧 token。

所以本协议的第一原则：**把裁决权、状态、停机条件全部外置到模型改不动的机械组件上**。
模型只保留它擅长的一件事：按台账顺序干活、留证据。

## 二、机制架构

```
driver.sh（外层无限循环，人类只按一次启动）
   │  每轮: 唤起 CLI 模型（opencode/claude/codex）执行 PROMPT.md
   │  模型会话结束后:
   ├─ loop_check.py --mode ledger   台账一致性（廉价，每会话后跑）
   │     rc=1 仍有未完成项 → 再唤起下一会话
   │     rc=3 剩余全 BLOCKED → 停机升级人工
   │     rc=0 台账全闭环 →
   └─ loop_check.py --mode full     现跑全量门禁+反假绿+git干净+终版报告
         rc=0 → 写 DONE 标记，停机（唯一合法完工）
         否则 → 继续循环
```

四个机械组件（模型被明令禁止修改它们）：

| 组件 | 职责 | 关键设计 |
|---|---|---|
| `audit_loop/loop2/LEDGER.md` | 唯一事实源（状态外置） | 9 列严格表格，机器解析；格式损坏=全员停工先修表 |
| `scripts/loop_gate.sh` | 通过/失败裁决（退出码） | quick=改动文件 ruff；full=十一关逐字复刻（含 MySQL 并发，MySQL 不可用直接 ABORT 禁止跳过）；日志强制落盘 gate-runs/ |
| `scripts/loop_check.py` | 完工裁决（唯一） | VERIFIED 必须证据文件真实存在非空；attempts>3 未 BLOCKED 判违规；BLOCKED 必须登记 ESCALATE；full 模式现跑门禁不信旧日志 |
| `audit_loop/loop2/driver.sh` | 坚持本身（不停机） | 模型每次会话只需干一项；"不停"由 bash 循环保证，不由模型意志力保证 |

## 三、状态机与断路器（防死循环的关键）

```
AUDIT ─→ VERIFIED（审查项：产出轮次文件+发现入台账）
TODO → REPRODUCED → FIXED → GREEN → VERIFIED（修复项：RED 先行，证据随流转）
任何非终态 → BLOCKED（attempts=3 强制；升级人工，禁止绕过）
```

- **复现前置**：TODO→REPRODUCED 必须先有失败测试/复现脚本的真实输出；复现不了直接
  断路器——继承项目纪律"禁止靠猜连续试三处以上"。
- **BLOCKED 阀门**：用户要求"不停"，但弱模型必有啃不动的项。阀门设计为"该项挂起+
  登记 ESCALATE.md+继续其余项"；当剩余全为 BLOCKED，loop_check 退出码 3，driver 停机
  并指明升级路径。**BLOCKED 不清零就不算交付完成**——full 校验只在全部 VERIFIED/WAIVED
  时放行，WAIVED 仅限专家/用户书面豁免。这样既防无限烧 token，又不放行带病交付。
- **批次门禁**：单项用 quick（秒级），每 5 项/每维度跑一次 full（约 12 分钟），收尾再
  由 loop_check --mode full 现跑一次——最终裁决永远基于新鲜运行，不信任历史日志。

## 四、防作弊面（本项目踩过的坑全部设卡）

| 历史坑 | 设卡点 |
|---|---|
| 假断言/恒真断言（E-02、模式 4） | full 校验强制跑 `check_fake_assertions.py`；RED 先行写入 PROMPT §3 |
| 门禁缩范围（模式 5，昨天的 monitor_gates 刚犯） | loop_gate.sh full 十一关逐字硬编码，模型无入口缩范围；AGENTS.md 条款 2 |
| 口头宣布通过 | 裁决权唯一定义为退出码（AGENTS.md 条款 2、PROMPT §4） |
| 证据缺失/漂移（E-09） | VERIFIED 行 evidence 必须真实存在非空文件；收尾强制基线同步自查 |
| 顺手改坏无关代码 | 禁止清单 + 单条目最小改动 + 单主题提交 |
| 改测试凑绿 | 禁止清单第 2 条 + 反假绿脚本 + 专家抽检（见 §六） |

## 六、专家角色不变（重要）

本协议让弱模型"干完"，不等于"干对"。本项目教训：开发模型全绿 ≠ 可交付
（925/708 环境差、mock 掩盖支付路径、自审批次仍需逐项抽检）。因此保留：

1. ESCALATE.md 的 BLOCKED 项由专家（本人）处置或给方案；
2. 每跑完一个批次门禁（或用户随时），把 driver.log + gate-runs/ + 台账交专家抽检——
   抽检重点：新增测试是否真 RED→GREEN、修复是否超出条目范围、基线数字是否同步；
3. 最终交付前，FINAL_REPORT.md 连同 DONE 标记交专家做终审（参照前八维审查口径）。

## 七、已知风险与取舍

- **token 消耗大**：每会话干一项 + full 门禁每批一跑，是用户明确要求的不计成本模式；
  driver 仍有 LOOP_MAX_ITERS 硬顶（默认 200 会话）防失控。
- **弱模型可能写坏台账表格**：loop_check 解析失败即停工报错（退出码 2），模型下一
  会话的启动仪式会先看到"修台账"指令——损坏不扩散。
- **opencode/claude/codex 无头模式差异**：driver 仅传一句话恢复口令，具体上下文加载
  依赖各 CLI 自动读 AGENTS.md（已验证三家均支持）；若宿主 CLI 换型，只改 driver case 分支。
- **MySQL 依赖**：full 门禁含 alembic check 与并发实证，MySQL 未启动时 ABORT（退出码 2）
  而不是跳过——宁可停，不放水（红线 5 口径）。

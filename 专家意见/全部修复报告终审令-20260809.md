## 审查维度（每项都要有结论）

### 1. 修复正确性

逐项按手册处方核对实现：最小改动、无顺手重构；边界条件（0/负值/上限/空值/软删/
已关闭态）；金额全程 Decimal + ROUND_HALF_UP 无 float 混入；LIKE 输入已 escape_like；
时区一律应用侧 datetime.now；行锁与 commit 同事务。对"一类 bug 全库枚举"的项（库存锁、
先查后改、唯一约束、提醒去重、分页截断等），独立 `rg` 全库复查是否仍有同构漏网点。

### 2. 测试真实性（重点，历史重灾区）

- RED 是否真红：随机抽 30% 项做"撤行复验"（临时还原缺陷行为，测试必须转红，验证后
  还原），资金/安全/并发项全量撤行复验；
- 断言是否守护行为而非实现细节；是否只测响应码不测结果值；是否互补数据陷阱（两口径
  结果相同、撤修复不红）；是否改旧断言糊弄；
- MySQL 并发项必须看 `scripts/verify_mysql_concurrency.py` 实测输出，SQLite 单测通过
  不算数；
- 全量 pytest 是唯一验收：单文件绿 ≠ 全量绿（全局 APScheduler 后台线程污染是已确认
  陷阱）。

### 3. 资金与安全专项（批次 1 全量亲验）

- F-077 账号接管：wx_login 任何路径不得返回他人用户、不得签发他人 token；
- F-084 重复打款：create_refund 前置校验 + 执行链状态守卫 + 行锁三层是否齐全，已退款
  订单再次发起必须被拒；
- F-001/002/003/004 库存与金额并发锁、F-023/024 路径遍历双重防御、F-046 定时任务直改
  状态、F-053 订单并发覆盖——逐项复现验证。

### 4. 迁移链与模型一致性

- alembic 迁移 050-055（当前 head=d3e4f5061728）逐一核对：模型列/类型/nullable/注释
  与迁移脚本逐字一致；唯一约束的存量清理与软删语义（对照 user.phone 全局唯一先例）；
- 本机 MySQL 实跑 `alembic upgrade head` + `alembic check` 零漂移；不得以"没环境"跳过。

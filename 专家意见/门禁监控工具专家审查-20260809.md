## 二、确认问题（全部本人实证复现）

### P1-1 交付物过不了项目门禁：ruff format --check 失败（模式 5：门禁缩范围）

**事实**：`venv/bin/ruff format --check scripts/monitor_gates.py` → `Would reformat: scripts/monitor_gates.py`（退出码 1）。交接卡 §七 门禁第一关是 `ruff check backend/ tests/ && venv/bin/ruff check features/ scripts/ && venv/bin/ruff format --check .`——全量跑必红。

**报告如何漏掉**：实现报告 §六 质量门禁表只贴了 `ruff check scripts/monitor_gates.py` 一行，**没跑 format --check**；交付摘要与 checkpoint §二十六 却写"ruff 0 告警"。这是错误记忆库模式 5（门禁命令缩范围）的又一次命中——门禁监控工具的交付者自己缩了门禁范围，讽刺但严重。

**修复方案**：`venv/bin/ruff format scripts/monitor_gates.py`（diff 我已看过，纯格式：行续接 `\` 改括号包裹、argparse 参数换行、f-string 拼接缩进，零逻辑变化），随后补跑 `ruff check features/ scripts/` + `ruff format --check .` 并在报告 §六 贴两关原始输出。

### P2-1 无半行缓冲：写端块缓冲 flush 断行时计数损坏 / DONE 丢失误报超时 / 段名丢失

**根因**：`main()` 轮询中 `f.readline()` 读到 EOF 时，**没有换行符的半行也会被消费**（`scripts/monitor_gates.py:250-257`），偏移直接推过断点；下一轮从断点后继续，一行被拆成两次 `process_line`。而门禁日志的写端（pytest/behave 重定向到文件）是块缓冲（8KB），flush 边界可以落在任意字节——这正是本工具要监控的场景，不是理论风险。

**实证复现**（对抗脚本逐场景输出，见附录 A）：

- C1：先写 `"91"`（无换行）再写 `"0 passed, 69 warnings..."` → 汇总 **passed=0**（正确值 910），工具把半行 `"0 passed"` 当成完整结果行。计数损坏。
- C2：`"===== GATES "` 与 `"DONE ====="` 分两次写 → DONE 标记两半都不等于完整标记（`:71` 精确相等判定）→ **监控直到超时，退出码 3 误报**，而门禁实际已完成。这是最坏失效模式：工具存在的意义就是"DONE 自动汇总退出"。
- C3：`"===== PYTE"` + `"ST ====="` 分段写 → 段名丢失，汇总 `段:` 清单缺 PYTEST。

**修复方案**（标准 tail 语义）：每轮读取时保留"断点前最后一个完整行"的边界——若 `readline()` 返回的最后一行不以 `\n` 结尾，记下该行起点偏移，`f.seek()` 回退到该起点，把这半行留到下一轮与新到内容拼接后再处理（或在内存缓冲该残行直到换行到达）。注意回退只影响未消费的半行，不会造成完整行重读/重复计数。修完补两条测试：半行拼接后计数正确、半行 DONE 能识别。

### P2-2 同 inode 截断重建不处理——规格 §三 明文要求"大小变化时重新打开"，实现只查 inode

**事实**：轮询中仅比较 `st_ino`（`scripts/monitor_gates.py:240-247`）。若文件被 `> file` 截断后重写（inode 不变、size 变小），文件偏移停在旧位置 → `readline()` 永远读不到新内容，直到文件重新长过旧偏移；期间的全部输出静默丢失。

**实证复现**：预先写入 3 行抬高偏移，监控运行中截断重写为 `77 passed + GATES DONE` → 工具 **passed=0、超时退出码 3**，文件里明明有 DONE。

**规格依据**：§三 实现要求逐字为"处理文件轮转/重建（inode **或大小**变化时重新打开）"。报告 §二 功能 1 也只声称"对比 inode"。这是明文规格条款未实现。

**修复方案**：每轮同时记录 `st.st_size`；`st_size < f.tell()` 即判定截断，重开文件从偏移 0 读（或 seek(0)）。补一条截断场景测试。

### P2-3 pytest 原生横幅污染段名清单（垃圾段带 ✓）+ 全小写 error 汇总行不判失败（假绿退出 0）

**事实一（段名污染）**：`SEGMENT_RE = ^=====\s*(.+?)\s*=====$`（`:41`）对等号数量不设防。pytest 自己的横幅是 6 等号（`====== 1 error in 0.12s ======`），前 5 个被锚点吃掉、第 6 个落进捕获组 → 被记录为段名 `"= 1 error in 0.12s ="` 并在汇总里打上 ✓。实测场景 H 汇总输出：`段: = 1 error in 0.12s =✓`。一次失败的 pytest 跑还会产出 `===== short test summary info =====`（恰 5 等号）、`=========== FAILURES ===========` 等横幅，全部变成带 ✓ 的"段"——**在恰恰最需要工具可信的失败场景下，汇总展示主动误导**。

**事实二（假绿）**：同一场景中 `!!!! Interrupted: 1 error during collection !!!!` 与 `====== 1 error in 0.12s ======` 全小写、无 failed/FAIL/ERROR/Traceback 关键字 → 均不判失败，工具 **退出码 0**。纯 collection error 的门禁跑（交接卡 §七 陷阱 10 的 edit 破坏 SyntaxError 正是这类事故）会被本工具判为全绿。大写 `ERROR tests/...` 行能被抓到（`:108`），所以该缺口是"只有汇总横幅"的尾部场景，但与段名污染叠加后观感极坏。

**修复方案**：
1. `SEGMENT_RE` 收紧为恰 5 等号且两侧不允许更多等号（如 `^=====[^=].*?[^=]=====$` 或等价负向断言），并可加白名单（PYTEST/BEHAVE/RUFF/CONTRACT/MODEL/WIRING/CONFIG/INTEGRATION/ALEMBIC/MYSQL）拒绝未知"段名"入清单——规格 §一 已枚举全部段名，白名单不违反"段名动态收集"（收集顺序仍动态）。
2. 错误判定补 `(\d+)\s+errors?\b`（pytest/behave 汇总的小写 error 计数，N>0 即失败）与 `Interrupted` 关键字。规格 §二.2 原文只写了大写 `ERROR`，此条属**规格补强**，建议先与规格作者（用户）确认再改，或在报告中显式声明裁决。
